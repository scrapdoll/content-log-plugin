# Кастомные статусы для каждого типа контента

## Принятые решения

- Встроенные 4 статуса (`planned` / `in-progress` / `finished` / `abandoned`) всегда присутствуют у каждого типа; кастомные — дополнения.
- Кастомный статус — **только метка**: запись в `fm['status']` не трогает даты `started`/`finished`; автопереходы прогресса на него не реагируют (кроме глобального правила «прогресс достиг тотала → `finished`», которое действует из любого статуса, как сейчас).
- Каждый статус имеет цвет из палитры Obsidian; встроенные сохраняют текущие цвета (запланировано — нейтральный, в работе — синий, завершено — зелёный, брошено — оранжевый).

## Модель данных

**`src/types.ts`**
- `export type ContentStatusId = ContentStatus | (string & {})` — id любого статуса (автодополнение для встроенных сохраняет).
- `StatusDef` → `{ id: string; label: string; color: StatusColor | null }`; `type StatusColor = 'blue' | 'green' | 'orange' | 'red' | 'yellow' | 'purple' | 'cyan' | 'pink'`.
- `STATUSES` получают поле `color` (текущие цвета).
- `toStatus()` заменить на `parseStatusId(value): ContentStatusId` — непустая строка проходит как есть (важно: неизвестный id больше не схлопывается в `planned`), иначе `'planned'`. Хелпер `labelForStatus(statuses, id): string` (fallback — raw id).
- `ContentItem.status` и `StatusFilter` (dashboard-model) → `ContentStatusId`.

**Настройки**: новый ключ `customStatuses: Record<ContentTypeId, StatusDef[]>` (только дополнения; ключи — любой известный тип, включая встроенные). По пути `customTypes` — сохранение в data.json через существующие `saveSettings`.

## Реестр

**`src/core/type-schema.ts`**: `normalizeStatusDefs(value, reservedIds)` — отбрасывает битые записи (id не по `KEY_PATTERN`, пустой label, неверный color, дубли, коллизии со встроенными id). `TypeSchema` получает поле `statuses: StatusDef[]` (заполняется при нормализации).

**`src/core/registry.ts`**: `rebuildTypeRegistry(customTypes, customStatuses)` — для каждого типа (встроенного и кастомного) склеивает `statuses = [...STATUSES, ...normalizeStatusDefs(customStatuses[id])]`. Новое: `getAllStatuses(): StatusDef[]` — объединение по всем типам с дедупом по id (label из первого вхождения) — для фильтра, сводки и экспорта.

**`src/main.ts`**: передать `settings.customStatuses` в `rebuildTypeRegistry` при загрузке.

## Переходы (минимальные правки)

**`src/core/frontmatter-transitions.ts`**
- `applyStatusChange(fm, status: ContentStatusId, today)`: параметр расширяется до `ContentStatusId`, в `switch` добавляется `default: break` — пользовательский статус пишет только `fm['status']`, даты не трогает.
- `applyProgressChange`: чтение текущего статуса через `parseStatusId` вместо `toStatus` — кастомный id не совпадёт ни с `planned`, ни с `finished`, поэтому ветки автопереходов его пропускают (а `parseStatusId(undefined) === 'planned'` сохраняет авто-старт для карточек без поля status). Иных изменений нет.

## Запись/чтение

- `src/core/mutations.ts`: `writeStatus`/`writeContentCard` — типы `ContentStatusId`; Notice и сравнение статусов — через `labelForStatus(schema.statuses, ...)` и `parseStatusId(fm['status']) !== input.status`.
- `src/core/scaffold.ts`: заменить дублированную инлайн-логику дат (строки 110–113) на вызов `applyStatusChange` — она теперь корректно обрабатывает и кастомные статусы.
- `src/core/content-item.ts:36`: `status: parseStatusId(fm['status'])`.

## UI

- **`src/commands/status.ts`** и **`src/ui/card-header.ts`**: список статусов из `getTypeSchema(item.type)?.statuses ?? STATUSES`.
- **`src/ui/add-content-modal.ts`**: dropdown из `schema.statuses`; при редактировании, если текущий статус карточки не входит в список (кастомный удалён из настроек) — добавить его отдельным пунктом, чтобы сохранение его не теряло. Дефолт при создании — `'in-progress'` (встроенный, всегда есть).
- **`src/ui/dashboard-controls.ts`** + **`dashboard-view.ts`**: опции фильтра статусов зависят от выбранного типа — конкретный тип → его `statuses`, «Все» → `getAllStatuses()`. При смене типа пересобрать опции (новый хелпер в controls) и сбросить `filterStatus` в `'All'`, если его id больше нет в списке.
- **`src/ui/dashboard-view.ts`**: расширить `schemasSignature()` полем `statuses` (иначе смена статусов не перерисует дашборд).
- **`src/ui/dashboard-summary.ts`**: чипы по `getAllStatuses()`; чип «Завершено за год» без изменений (считает по дате `finished`).
- **`src/commands/export.ts`**: секции по `getAllStatuses()` с lookup'ом label.
- **Цвета пилюль**: `card-header.ts` и `dashboard-items.ts` рендерят `cl-status` без id-модификатора + inline `style="--cl-status-color: var(--color-…); --cl-status-border: var(--color-…)"` (если color задан). В **`styles.css`** перевести `.cl-status--*` на `var(--cl-status-color, var(--text-muted))` / `var(--cl-status-border, var(--background-modifier-border))`; `.cl-status-option` не меняется.

- **`src/settings.ts`**: подключить панель `<details class="cl-settings-panel">` «Статусы» после секции типов; ключ `customStatuses` в интерфейсе, дефолте и `normalizeSettings`.

## Тесты (vitest)

- `frontmatter-transitions`: кастомный статус не трогает даты; авто-финиш по тоталу из кастомного; частичный прогресс из кастомного → статус не меняется; карточка без `status` авто-стартует.
- Реестр: слияние `customStatuses`, отбрасывание дублей/коллизий/битых.
- `content-item`: кастомный id проходит насквозь, мусор → `planned`.
- `dashboard-model`: фильтрация по кастомному id.
